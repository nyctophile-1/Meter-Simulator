AWS Deployment Runbook — Maya Sim (Meter Simulator)

Click-by-click deployment guide. Every field is named; anything not listed = leave default. Steps marked ⚠️ will silently fail later if skipped or done incorrectly.

Stage 7 — Collect 3 Values

  1. Instances → click your instance → Networking tab. Write down:
    • Public IPv4 address → call it PUBIP
    • IPv6 address → call it INSTIP
  2. Same tab → scroll to Network interfaces → click the Interface ID link (eni-…).
  3. On the ENI page → Details tab → find IPv6 delegated prefixes (or "IPv6 Prefix Delegation").
  4. Copy it exactly, e.g. 2406:da1a:1c29:500:bc96::/80 → call it NEWPREFIX.
    ⚠️ If this field is empty, step 6.7 didn't take. Fix without relaunching: 
    aws ec2 assign-ipv6-addresses --network-interface-id eni-XXXXXXXX --ipv6-prefix-count 1
  5. NEWPREFIX minus the /80, plus 1 = your first meter address. Example: prefix 2406:da1a:1c29:500:bc96::/80 → first meter 2406:da1a:1c29:500:bc96::1. Call it METER1.

Stage 9 — Build

Open PowerShell, then:

cd "C:\Users\ayush\OneDrive\Documents\Development\Sinhal Repos\Meter-Simulator"

If Stage 8 updated the $ExpectedPrefix default in build.ps1, just run:

.\deploy\build.ps1

Otherwise pass it explicitly:

.\deploy\build.ps1 -ExpectedPrefix '<NEWPREFIX>'

Expect: Passed! Failed: 0, Passed: 50 → prefix OK: <NEWPREFIX> → Built …\publish\maya-sim.tar.gz (≈50 MB, 4 templates), then the scp/ssh commands printed with the correct host.

⚠️ The build aborts if appsettings.Production.json and -ExpectedPrefix disagree. That guard only compares those two — if both still hold an old prefix it passes happily and produces a build whose meters are unreachable. Stage 8 must change all three files.

Add -SkipTests only if you are in a hurry; it skips the 50-test gate.

Stage 13 — Prepare the Host

Installs libicu, the service user, /opt/maya-sim, swap, kernel tuning, the local meter route, the route watchdog, and both systemd units. It is idempotent — safe to re-run on a live host, and it does not touch the app or your data.

sudo bash /tmp/host-prep.sh
⚠️ Last line must be OK: the kernel owns the meter prefix.
If it says FAIL → Stage 8 line 15 is wrong. Fix, re-upload, re-run.

⚠️ One mandatory re-run right now. host-prep.sh gained a route watchdog that does not exist on hosts prepared before it was added. Until you re-run Stage 13 once, the box is still exposed to the failure described below.

Confirm the watchdog is armed

systemctl list-timers maya-meter-route-check --no-pager

→ a NEXT time within 60 seconds. If the timer is missing, the watchdog did not install — re-run Stage 13.

Why the watchdog exists. The local meter route is not owned by netplan/networkd, so anything that reconfigures the interface (DHCPv6 renewal, netplan apply, networkd restart, link flap) silently flushes it. maya-meter-route is Type=oneshot RemainAfterExit=yes, so systemd still reports it active and never re-runs it.

The symptom is distinctive: the UI on port 80 keeps working while every meter times out — and it is a timeout, not "connection refused". A refused connection means the app is down; a timeout with no response means the address is not local, i.e. the route is gone. The watchdog re-asserts it every 60s with ip -6 route replace, which is idempotent and atomic, so recovery is automatic and needs no restart.

Stage 14 — Deploy

sudo bash /tmp/deploy.sh /tmp/maya-sim.tar.gz

Expect, in order: Re-asserting meter route → active → a log block → listeners on 4059 and 80 → OK: <METER1> resolves as local.

⚠️ If the last line reads WARNING: … is NOT local, meters will time out even though the service is active and the UI works. Fix without redeploying: 
sudo systemctl restart maya-meter-route maya-sim
Your data survives a redeploy. deploy.sh replaces only /opt/maya-sim/app/. The siblings data/ and logs/ are never touched, so batches (data/batches.json) and runtime config such as the network delay (data/maya-runtime-config.json) both persist. The previous release is kept at app.prev for rollback.

Stage 15 — Change the Passwords

sudo mkdir -p /etc/maya-sim && sudo nano /etc/maya-sim/secrets.env

Type these three lines (letters/numbers only — no quotes or symbols):

Auth__AdminPassword=<yourAdminPw>
Auth__UtilityPassword=<yourUtilityPw>
Auth__ViewerPassword=<yourViewerPw>

Save in nano: Ctrl+O → Enter → Ctrl+X.

sudo chown root:root /etc/maya-sim/secrets.env && sudo chmod 600 /etc/maya-sim/secrets.env && sudo systemctl restart maya-sim

Stage 16 — Verify in Order

On the instance

systemctl is-active maya-sim

→ active

journalctl -u maya-sim -n 40 --no-pager | grep -i "prefix\|bound"

→ shows [::]:4059 and your NEWPREFIX — ⚠️ if it shows fd00: the config didn't ship

ip -6 route get <METER1>

→ the output contains the word local

curl -sv --max-time 5 "http://[<METER1>]:4059" 2>&1 | head -5

→ Connected to (an HTTP error after it is normal — that port speaks DLMS)

Test-NetConnection <METER1> -Port 4059

→ TcpTestSucceeded : True

Then browse to http://<PUBIP>/ and log in with your new admin password.

Reading a failure: instance checks pass but laptop fails ⇒ the fault is AWS (Stage 6.7 prefix or Stage 4 rule 5), never the app.

Later Redeploys

Only Stages 9 → 11 → 12 → 14.

Skip Stage 13 unless host-prep.sh changed in the repo, the meter prefix changed, or the box was rebuilt — see the table in Stage 13. Stage 11 already uploads host-prep.sh alongside the tarball, so re-running it is just one extra command when you do need it.

After any redeploy, the 5-second check that the whole chain is live:

curl -sv --max-time 5 "http://[<METER1>]:4059" 2>&1 | grep -i connected

→ Connected to means route + socket are both good. Silence means the route is missing (see Stage 13).

Troubleshooting: UI works but meters time out

The most common failure on this deployment. Work down the list — each step rules out a layer.

SymptomMeaning
Connection refused (fast)App is down or not listening → systemctl status maya-sim
Connection times out (slow, no reply)Packet never reached a socket → the local route is gone, or an AWS-side problem
 
ip -6 route show table local | grep 2406

→ must list your <NEWPREFIX>. If it does not, that is the fault:

sudo systemctl restart maya-meter-route maya-sim

If the route is present and it still times out from your laptop, the fault is AWS, not the host — check the ENI still holds the delegated prefix and that security-group rule 5 (TCP 4059 from ::/0) is intact.

Do NOT Do These

Tried in the previous deployment, none delivered traffic:

  • Route-table entry for the meter range
  • IGW edge association
  • A separate subnet for meters
  • Disabling the ENI source/dest check

Other gotchas:

  • Template filenames are case-sensitive on Linux
  • Stop/start changes PUBIP (prefix and IPv6 survive)
  • "Launch more like this" silently drops the auto-assign settings
Console labels can shift slightly between AWS UI revisions — if a label doesn't match exactly, use the closest equivalent option.
