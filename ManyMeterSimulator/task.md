## Phase 9 — UI & All-In-One Control Plane (see implementation.md §10)
- [x] Convert `ManyMeterSimulator` from `Microsoft.NET.Sdk.Worker` to `Microsoft.NET.Sdk.Web` — `TcpNicListenerService` and all existing components (`ConnectionRegistry`, `SimulatorMetrics`, `IMeterSimBridge`, etc.) keep working unchanged, still a hosted `BackgroundService`, just under an ASP.NET Core host (`WebApplication.CreateBuilder`) instead of a plain Generic Host. Verified: TCP listener still binds and logs exactly as before, alongside Kestrel now serving the dashboard.
- [x] Add Blazor Server, basic layout/nav (`Components/App.razor`, `Routes.razor`, `Layout/MainLayout.razor`) — MAYA branding in the page title and header, nowhere else
- [x] **Batch-based `MeterRegistry`** (`Provisioning/MeterRegistry.cs`, `MeterBatch.cs`, `BatchStatus.cs`, `MeterAddressing.cs`) — superseded the earlier flat-list version. Batches are the real provisioning unit: `AddBatch(name, count)` reserves a contiguous index range *without* starting it (`NotStarted`), `TryStart`/`TryStop`/`Delete` transition it, each new batch continues from wherever the last left off. Each index deterministically maps to both an IP address and a meter serial number (`MYnnnnnnnnn`, 9-digit zero-padded, capped at `MaxIndex = 999,999,999` — "one shy of a billion"; originally 9,999,999/7 digits, bumped 100x — purely a serial-format choice, not a network limit, and free to do since `AddBatch` is O(1) regardless of batch size). Address computation extracted into shared `MeterAddressing.ComputeAddress`/`ExtractIndex` (byte-level, spans the full 64-bit host portion of the /64 — **not** naive string concatenation, which breaks past 65,535); `HESTestClient` updated to use the same helper for consistency.
- [x] **Batch status actually gates the TCP listener** (`TcpNicListenerService`, injects `MeterRegistry`) — a connection to a meter in a `NotStarted` or `Stopped` batch is rejected immediately (logged, counted via `SimulatorMetrics.RecordRejectedBatchNotRunning`); meters never assigned to any batch keep the old permissive behavior. New `SimulatorMetrics` counter: `TotalRejectedBatchNotRunning`.
- [x] Setup page (`Components/Pages/Setup.razor`, at `/`) rebuilt around batches: name + N inputs, live preview of the range `Add Batch` would reserve (IPs *and* meter numbers), a batch table (Name/Count/IP range/Meter# range/Status/Actions), Start/Stop/Delete per row, click-a-row to expand and see the full IP↔meter-number list (capped at showing 50, `...and N more`).
- [x] **Verified live, full lifecycle, including real TCP behavior** (not just UI state): added a batch (`NotStarted`) → confirmed `HESTestClient` connection to it was rejected with `batch is NotStarted` in the log → clicked Start → same connection now succeeds (3/3 exchanges) → clicked Stop → same connection rejected again (`batch is Stopped`) → expanded the row and confirmed all 10 IP↔meter-number pairs → deleted the batch, confirmed it disappeared and its range was *not* reclaimed (next preview continued past it, by design - reclaiming freed ranges would need a more complex allocator, not worth it for "delete, for now").
- [x] **Real bug fixed**: the original single-group hex-formatting scheme (`$"{prefix}{index:x}"`) crashed with `FormatException` once the running index exceeded 65,535 (discovered live via the Blazor UI - an unhandled exception on the server took down the whole circuit, which is what looked like the page "getting stuck"). Fixed by computing addresses at the byte level instead (spans the full 64-bit host portion correctly); covered by dedicated unit tests including the exact 65,535/65,536 boundary. Also fixed a locale-formatting bug (batch counts were rendering as `99,99,999` Indian-style grouping instead of `9,999,999`, since the server's default culture is `en-IN`) — numeric displays now force `CultureInfo.InvariantCulture`.
- [x] Unit tests (`ManyMeterSimulator.Tests/MeterRegistryTests.cs`): 9 new tests covering small-count addressing, the group-boundary carry-over, sequential batches, preview correctness, zero/negative count rejection, max-index cap enforcement (and that a failed over-cap attempt doesn't partially consume the range), serial formatting, and status transitions/gating. 16/16 total passing.

One password per role (not per-user accounts), configured in `appsettings.json` under `Auth:*`. Permission model, additive (Admin ⊇ Utility ⊇ Viewer): **Viewer** — view only, no controls at all. **Utility** — view + Start/Stop. **Admin** — view + Start/Stop + Add Batch/Delete. Login grants all roles a login is entitled to as claims up front (e.g. an Admin login carries Admin+Utility+Viewer claims), so permission checks are single `IsInRole(...)` calls, not OR-chains. Setup page requires `[Authorize]` (redirects to `/login` if not authenticated, via `RedirectToLogin.razor` + `AuthorizeRouteView`); Add Batch/Delete are Admin-only and Start/Stop are Utility+ **both** in the UI (buttons hidden entirely per role) **and** re-checked server-side in the handler methods (defense in depth — a hidden button isn't the only thing stopping the action).
